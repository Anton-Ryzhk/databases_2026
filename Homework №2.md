# Часть 1. Дополнение схемы

## 1.1. Какие таблицы добавляются

Добавляются две новые таблицы:

1. **`edtech.tag`** — справочник тегов / направлений обучения.  
   Например: `SQL`, `PostgreSQL`, `Backend`, `Аналитика данных`.

2. **`edtech.course_tag`** — связная таблица для отношения **многие-ко-многим** между курсами и тегами.  
   Один курс может иметь несколько тегов, один тег может относиться к нескольким курсам.

Это расширение полезно для частых запросов каталога: фильтрация и поиск курсов по направлениям, тегам, тематикам.

---

## 1.2. Реализация отношения M:N

Логическое отношение:

```text
COURSE }|----|{ TAG
```

Один курс может иметь много тегов.  
Один тег может быть назначен многим курсам.

В реляционной модели такое отношение реализуется через промежуточную таблицу:

```text
COURSE 1 ---- M COURSE_TAG M ---- 1 TAG
```

### Почему выбрана именно связная таблица

| Альтернатива | Почему не подходит |
|---|---|
| Хранить теги массивом в `course` | Нарушается нормализация, сложно обеспечить ссылочную целостность, сложно искать курсы по тегу |
| Хранить теги в `JSONB` | Удобно для документов, но хуже для строгих связей, уникальности тегов и эффективных JOIN-запросов |
| Отдельная таблица `course_tag` + справочник `tag` | Обеспечивает целостность, уникальность, индексацию, фильтрацию и поддержку M:N |

В таблице `course_tag` выбран составной первичный ключ:

```sql
PRIMARY KEY (course_id, tag_id)
```

Это гарантирует, что один и тот же тег нельзя назначить одному и тому же курсу дважды.

## 1.3. Что будет при `DROP CASCADE`

Здесь важно различать:

1. **`ON DELETE CASCADE`** — поведение при удалении строк через `DELETE`.
2. **`DROP TABLE ... CASCADE`** — удаление самой таблицы как объекта базы данных.

### Поведение `ON DELETE CASCADE`

Для таблицы `course_tag` заданы внешние ключи:

```sql
FOREIGN KEY (course_id) REFERENCES edtech.course(course_id) ON DELETE CASCADE
FOREIGN KEY (tag_id) REFERENCES edtech.tag(tag_id) ON DELETE CASCADE
```

Это означает:

- если удалить курс, то все его связи из `course_tag` будут удалены автоматически;
- если удалить тег, то все его связи из `course_tag` будут удалены автоматически;
- после удаления не останется «осиротевших» строк в `course_tag`.

При этом удаление самого курса может быть ограничено другими таблицами, например `enrollment`, если в ДЗ №1 там стоит `ON DELETE RESTRICT`.

### Поведение `DROP TABLE ... CASCADE`

Если выполнить:

```sql
DROP TABLE edtech.tag CASCADE;
```

PostgreSQL удалит таблицу `tag`, а также зависимые объекты, например внешние ключи из `course_tag`, которые ссылаются на `tag`.

Но сама таблица `course_tag` при этом не будет автоматически удалена полностью, если не выполнить:

```sql
DROP TABLE edtech.course_tag;
```

Поэтому в скрипте ниже таблицы удаляются в правильном порядке:

```sql
DROP TABLE IF EXISTS edtech.course_tag CASCADE;
DROP TABLE IF EXISTS edtech.tag CASCADE;
```

Это обеспечивает повторяемость скрипта и отсутствие «повисших» зависимостей.

## 1.4. Индексы и частые запросы из ДЗ №1

В ДЗ №1 были перечислены типовые запросы:

1. Личный кабинет студента: мои активные курсы и прогресс.
2. Каталог курсов: опубликованные курсы, рейтинг, число записей.
3. Страница курса: программа курса, отзывы, уроки.
4. Личный кабинет преподавателя: доходы, отчисления, студенты.
5. Доступ к уроку: проверка записи студента и получение контента урока.

Добавленные и уже существующие индексы учитывают эти сценарии:

| Типовой запрос | Используемые индексы |
|---|---|
| Мои курсы студента | `enrollment(user_id, status)`, первичный ключ `enrollment(user_id, course_id)` |
| Каталог опубликованных курсов | частичный индекс по `course(created_at DESC) WHERE is_published` |
| Средний рейтинг курса | `review(course_id, rating)` |
| Количество записей на курс | `enrollment(course_id)` |
| Курсы преподавателя | `course(instructor_id)` |
| Статистика по времени записей | `enrollment(course_id, enrolled_at DESC)` |
| Теги курса | первичный ключ `course_tag(course_id, tag_id)` |
| Курсы по тегу | `course_tag(tag_id)` |

Ниже приведена таблица для каждого из пяти продемонстрированных случаев.

| № | Ограничение | Выполняемый запрос | Сообщение СУБД | Понятное сообщение для пользователя | Как исправить |
|---:|---|---|---|---|---|
| 1 | `CHECK` | `INSERT INTO edtech.tag (name) VALUES ('x');` | `new row for relation "tag" violates check constraint "chk_tag_name_length"` | «Название тега должно содержать минимум 2 символа» | Указать корректное название тега длиной от 2 до 100 символов |
| 2 | `FOREIGN KEY` | `INSERT INTO edtech.course_tag (course_id, tag_id) VALUES (<несуществующий course_id>, <существующий tag_id>);` | `insert or update on table "course_tag" violates foreign key constraint "fk_course_tag_course"` | «Нельзя привязать тег к несуществующему курсу» | Использовать существующий `course_id` или сначала создать курс |
| 3 | `UNIQUE` | Вторая попытка: `INSERT INTO edtech.tag (name) VALUES ('Тег_1');` после уже выполненной вставки такого же имени | `duplicate key value violates unique constraint "uq_tag_name"` | «Тег с таким названием уже существует. Выберите уникальное название» | Изменить название тега или использовать уже существующий тег |
| 4 | `NOT NULL` | `INSERT INTO edtech.tag (name) VALUES (NULL);` | `null value in column "name" of relation "tag" violates not-null constraint"` | «Тег не может быть создан без названия» | Передать непустое значение `name` |

Повторное назначение запрещено» | Не вставлять дублирующую связь или сначала удалить существующую строку из `course_tag` |
