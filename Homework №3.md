### Q1 (Уникальные рейсы и сортировка)

**1. Отличия DISTINCT и GROUP BY**
*   Логически результаты будут идентичны. Оба оператора возвращают уникальные значения flight_no.
*   По плану выполнения они могут отличаться. Обычно DISTINCT просто сортирует данные и убирает дубли, а GROUP BY использует хеширование. Но в современных версиях PostgreSQL оптимизатор часто делает для них одинаковый план. Еще DISTINCT может использовать индекс, если он есть, а GROUP BY не всегда.

**2. Сортировка без `ASC` и регистр**
*   Почему достаточно ORDER BY: В PostgreSQL сортировка по умолчанию всегда возрастающая.
*   Верхний и нижний регистр: символы верхнего регистра имеют меньший код, чем нижнего. Поэтому 'PG0001' встанет раньше, чем 'pg0001'.

### Q2 (Аэропорты и выручка за билеты)

**1. Дубликаты пассажиров и `COUNT(*)`**
*   Если пассажир купил два билета, в таблице ticket_flights (или tickets) появятся две записи.
*   SUM(amount) отработает корректно и посчитает общую выручку за оба билета.
*   `COUNT(*)` посчитает количество строк (билетов), а не уникальных пассажиров. Произойдет двойной счет. Чтобы посчитать именно пассажиров, нужно использовать COUNT(DISTINCT passenger_id).

**2. Рейс без проданных билетов**
*   При использовании INNER JOIN рейс без билетов исчезнет из выборки, так как для него нет пар в правой таблице.
*   Чтобы рейс попал в результат с нулевой выручкой, нужно использовать LEFT JOIN.

### Q3 (Отмененные рейсы и города)

**1. Аэропорт без рейсов в flights**
*   Чисто логически, если из города вообще не было рейсов, то утверждение «из города не было отправлено ни одного отмененного рейса» является истинным. Такой город попадает в результат.
*   И NOT IN, и NOT EXISTS корректно включат этот город в выборку, так как подзапрос просто не найдет для него совпадений.

**2. Ловушка NOT IN с NULL**
*   Если подзапрос `SELECT departure_airport ... WHERE status = 'Cancelled'` вернет хотя бы один NULL, то конструкция `city NOT IN (...)` сломается, потому что NOT IN  с NULL дает UNKNOWN. UNKNOWN в WHERE интерпретируется как FALSE. Результат запроса будет пустым.
*   Почему NOT EXISTS лишен этой проблемы: NOT EXISTS проверяет наличие строк, а не сравнивает значения напрямую. Он просто ищет совпадение.

### Q4 (Места на борту и дубликаты)

**1. Дубликаты посадочных талонов**
* Правильнее использовать DISTINCT, так как мы хотим убрать дубликаты строк. Но по сути оптимизатор сделает для них одинаковый план, так что по эффективности разницы быть не должно.
**2. Сданный билет, но есть посадочный**
*   Для таких случаев, лучше хранить статус билета, тогда появляется возможность добавить фильтр в условии WHERE или JOIN, например : `WHERE t.status != 'REFUNDED'`

### Q5 (DDL и блокировки на живой таблице)

**1. ADD COLUMN против SELECT**
*   Команда ALTER TABLE ... ADD COLUMN (без DEFAULT или с DEFAULT NULL) требует блокировки уровня ACCESS EXCLUSIVE.
*   Долгий SELECT держит блокировку ACCESS SHARE.
*   Эти блокировки конфликтуют. Ваша DDL-команда встанет в очередь и будет ждать (блокироваться), пока транзакция с SELECT не завершится.

**2. Мгновенное добавление колонки с DEFAULT в PG 11+**
*   Начиная с PostgreSQL 11, добавление колонки с константным DEFAULT не переписывает таблицу. PG просто добавляет метаданные в системный каталог (pg_attribute и pg_attrdef).
*   **Как это работает:** Когда вы читаете старую строку, PG видит, что в физическом кортеже (tuple) нет данных для новой колонки, и подставляет значение из `pg_attrdef` на лету.
*   **Что будет при изменении DEFAULT:** Если позже вы сделаете `ALTER COLUMN ... SET DEFAULT true`, значение по умолчанию в системном каталоге изменится. Все существующие строки, которые не были физически обновлены (для которых колонка отсутствовала в кортеже), начнут возвращать новое значение (true).
**3. Создание индекса и блокировки**
*   Обычный CREATE INDEX берет блокировку SHARE, которая разрешает чтение(SELECT), но блокирует запись (INSERT, UPDATE, DELETE).
*   Решением будет использование синтаксиса CREATE INDEX CONCURRENTLY. Он строит индекс в два прохода, не блокируя модификации данных.
*   Почему это компромисс:
    1. Это работает значительно дольше, так как индекс строится в фоновом режиме с учетом параллельных изменений.
    2. CONCURRENTLY нельзя использовать внутри транзакции.
    3. Если в процессе построения произойдет ошибка (или вы отмените запрос), индекс останется в базе в статусе INVALID. Его нужно будет вручную удалить.

### Q6 (Агрегация и NULL в вычислениях)

**1. AVG и NULL в задержках**
*   Все агрегатные функции (кроме `COUNT(*)`) игнорируют NULL.
*   Если actual_departure равно NULL(рейс отменен), эти строки просто исключатся из расчета.
*   Влияние на результат: Среднее будет посчитано только по тем рейсам, которые фактически вылетели. Делитель в формуле среднего (`SUM / COUNT`) уменьшится. 

**2. COUNT(aircraft_code) vs `COUNT(*)`**
*   `COUNT(*)` считает количество строк (кортежей) в таблице.
*   COUNT(aircraft_code) считает количество не NULL значений в колонке aircraft_code.
*   Результаты будут одинаковыми только если на колонку aircraft_code наложено ограничение NOT NULL в схемы таблицы. Если ограничения нет и в таблице есть строки с NULL в aircraft_code, то COUNT(aircraft_code) будет меньше, чем `COUNT(*)`.
